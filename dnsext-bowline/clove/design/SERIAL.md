# clove: シリアルと署名の設計

clove のシリアルと署名に関する設計書です。

## 想定する運用

| | source | signing | 役割 |
|---|---|---|---|
| A | ファイル | no | 署名しない primary |
| B | ファイル | yes | 署名する primary |
| C | IP アドレス | no | secondary。上流から RRSIG 付きのレコードを受け取り、そのまま配る |
| D | IP アドレス | yes | 上流から署名の無いゾーンを受け取り、署名する primary |

- 署名するかどうかは、設定の `signing` で決めます。
- 上流が署名済みのものを渡すか否かは、運用時の取り決めです。
- 上流が署名済みなのに `signing: yes` のときは、読み込みを拒否します。

## 設計

### シリアル
- 署名するゾーン（B と D）は、2 つのシリアルを別々に持ちます。
  - **上流のシリアル**：上流（D では上流のサーバ、B ではゾーンファイル）が示す値です。D では、上流に新しい版があるかを比べるためだけに使います。
  - **自分のシリアル**：clove が SOA に載せて、下流に見せる値です。
- 自分のシリアルは、ゾーンの中身を変えるたびに上げます（RFC 1034 Sec 4.3.5）。新しい値は次のとおりです。
  - 上流のシリアルの方が大きければ、上流の値に合わせます。
  - そうでなければ、1 を足します（RFC 1982 の算術）。
- 中身を変えない読み込み（上流が `Unchanged`、同じゾーンファイルの読み直し）では、シリアルを上げません。
- 署名しないゾーン（A と C）は、上流のシリアルをそのまま見せます。
- 自分のシリアルと、D の上流のシリアルは、ゾーンのディレクトリにファイルとして保存し、再起動しても戻らないようにします（[CLOVE-DIR.md](CLOVE-DIR.md)）。B の上流のシリアルは、ゾーンファイルに書いてある値です。

### 署名し直す契機
- 署名し直すのは、次の 2 つの場合だけです。
  - 上流から新しい版を受け取ったとき。起動して最初の読み込みは、新しい版として扱います。
  - ZSK のロールオーバーの時期が来たとき。鍵の生成に失敗した場合も含みます。
- `rrsig-lifetime` は、`zsk-rollover-duration` の 4/3 倍以上に限っています。そのため、ロールオーバーのたびに署名し直せば、clove 自身の RRSIG が期限切れになることはありません。
  - 余裕（既定値では 10 日 − 7 日 = 3 日）が、下流が転送するまでの猶予になります。
- 署名し直したら、自分のシリアルを上げて、NOTIFY を送ります。

### 鍵
- KSK は 1 本です。ロールオーバーの仕組みは持ちません。DS の更新を伴うので、運用者が手で行います。
- ZSK は、新しい順に 3 本（前、今、次）を公開し、「今」の 1 本で署名します。
  - `zsk-rollover-duration` ごとに新しい鍵を 1 本作り、1 つずつずらします。
  - 3 本を公開しているので、clove と下流とで、ロールオーバー 1 回分のずれまでは検証が通ります。
- アルゴリズムは設定で決め、鍵ファイルと違えば拒否します（#309）。

### NOTIFY
- 自分のシリアル（A と C では上流のシリアル）が変わったときだけ送ります。

### 上流への要求
- ありません。上流は、中身を変えたときにシリアルを上げるだけで済みます。clove の都合でシリアルを上げてもらう必要はありません。

## 参考：ほかの実装（公式ドキュメントで確認）
- **BIND の inline-signing**（primary と secondary で使える）
  - 署名した版のシリアルを、署名していない版とは別に持ちます。
  - 署名していない版のシリアルの方が大きくなれば、署名した版もそれに合わせます。上げ方は `serial-update-method` で選べます。
- **Knot DNS**
  - 自動署名のあとのシリアルの上げ方を、`serial-policy` で選べます。
  - `zonefile-load: difference-no-serial` では、ゾーンファイルのシリアルを無視して、サーバがシリアルを上げます。
